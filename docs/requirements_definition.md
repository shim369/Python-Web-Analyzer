# サイトリニューアル可否自動判定ツール 要件定義書

## 1. 機能要件

### 1.1. ファイル入出力機能

* **Excelインポート**:
  * `B列（サイト名）`に純粋なドメイン名が記載されたExcelファイル（`.xlsx`）を受け取る（B列が空の行はA列を代替参照する）。
  * ヘッダー行（`サイト名`という値の行）はスキップする。
  * システムは自動的に、本物のブラウザに擬態したヘッダー（WAF・セキュリティブロック回避用）を用いてアクセスを試みる。
  * インポート時に判定閾値（`page_threshold`）を指定するUIは現状**存在しない**。常にデフォルト値 `10` で運用される。

* **Excelエクスポート**:
  * 解析完了後、元の行順を完全に維持したまま、A列に実行日の日付（`M/D` 形式）、C列〜O列に解析・判定結果をマージして出力する。
  * ヘッダー行はネイビー背景（`#1F4E78`）・白文字・太字でスタイリングし、罫線・自動列幅調整（全角文字は2文字分としてカウント）を適用する。
  * セル内の制御文字（改行以外の`\x00`〜`\x1F`）は出力前に除去する。

### 1.2. 各列のデータ取得・出力ロジック仕様

| 列 | 項目名 | データ型 | 処理・取得・判定ロジック |
| --- | --- | --- | --- |
| **A** | 日付 | 文字列 | アプリ実行時の日付を `M/D` 形式（例: `7/16`）で出力。 |
| **B** | サイト名 | 文字列 | インポートされたドメイン名（そのまま維持）。 |
| **C** | 調査結果 | 文字列 | **`◯` / `×` / `要確認` の3値。** 以下の優先順位で判定する。<br><br>【最優先・要確認判定】<br>(1) 接続エラー、タイムアウト、ボットブロック等で総ページ数が **0** の場合 ➔ **『要確認』**（理由: 接続不可またはアクセス拒否のため、判定を保留しました。）<br>(2) 取得ページ数が **1〜2ページ** の場合 ➔ **『要確認』**（理由: クロールできたページ数が極端に少ないため判定を保留しました。）<br>(3) 階層数が深すぎて計測できない場合（`max_depth == "要確認"`、実クロールで階層10超過時）➔ **『要確認』**（理由: サイト階層が深すぎるため、別途サイトエクスプローラー等での確認をお願いします。）<br><br>【上記に該当しない場合の◯/×判定】(`RenewalEvaluator.evaluate` に委譲)<br>以下のいずれか1つでも該当すれば **`×`**、いずれにも該当しなければ **`◯`**。該当理由はすべてM列に改行区切りで列挙される。<br><br>*ページ構成・機能面*<br>・ページ数が `page_threshold`（デフォルト10）を超える<br>・階層数が3階層以上（`max_depth > 2`）<br>・ログイン／マイページ機能を検出<br>・お問い合わせフォームに添付（ファイル）機能を検出<br>・ベーシック認証（401 Unauthorized）がかかっているページを検出<br><br>*お問い合わせフォームの仕様*<br>・画像認証（Captcha）を使用<br>・ステップ型（複数画面に分割された）入力フォーム<br><br>*専用機能*<br>・カレンダー機能<br>・サイト内検索・絞り込み検索機能<br>・チャットボット導入<br>・PDF資料・ダウンロードデータが多い（PDFリンク数が`PDF_LINK_THRESHOLD`＝デフォルト5件以上）<br><br>*リッチコンテンツ*<br>・Lightbox / Fancybox 等のギャラリー機能を検出<br>・多言語切り替え機能（Google翻訳、言語セレクタ等）を検出<br>・GSAP / ScrollTrigger / AOS 等のスクロールアニメーションを多用<br><br>※旧仕様の `◎`（優良）/`△`（要検討）の2段階は廃止され、判定は2値（◯/×）に簡素化されている。<br>※Google Map埋め込み、トップページの動画、フローティングボタン、アコーディオン／タブ／モーダル、ブログ・お知らせ・採用ページ・実績ページのボリューム等は、現代の一般的なコーポレートサイトの大半が該当してしまい判定基準として機能しにくいため、意図的に不可理由に含めていない。 |
| **D** | SSLあり | 文字列 | `http://` からの接続を追跡、または個別に `https://` 接続を検証し、有効なSSL証明書が確認できれば **「あり」**、不可の場合は **「なし」**、両方とも接続に失敗し判定不能な場合は空欄。 |
| **E** | SSL常時 | 文字列 | `http://` へのアクセスが自動的に `https://` へリダイレクトされることが確認できれば **「◯」**。リダイレクトなくHTTPのまま到達できた場合は **「×」**。`http://` 自体に接続できず（ポート80非対応など）、フォールバックで `https://` へ直接接続し成功した場合も、実質的にSSLのみで到達可能なサイトとして **「◯」** 扱いとする。両方とも失敗した場合は空欄。 |
| **F** | 階層数 | 整数 or 文字列 | URLパスのセグメント数（＋トップページ分の1）を基準とする最大階層数。**階層数が10を超える場合は数値ではなく `"要確認"` という文字列を返す**（判定を自動化せず、別ツールでの目視確認に委ねるための仕様）。 |
| **G** | svcmd | 文字列 | 常に**空欄**（NULL値）として出力。 |
| **H** | 構成 | 文字列 | トップページのHTMLからグローバルナビゲーションを自動検出。多言語切り替えメニュー等は除外した上で、メニューテキストを**改行区切り**で最大10件表示。 |
| **I** | ページ数 | 整数 | 同一ドメイン内のすべての内部リンク（通常の`<a>`タグに加え、`onclick`等によるJS遷移リンクも含む）を巡回し、総ページ数を集計。巡回上限は100ページ、または設定されたタイムアウト（デフォルト30秒）まで。<br><br>接続時にタイムアウトやエラーが発生した場合は「0」を出力。100ページに到達した場合はExcel出力時に「100~」へ変換。 |
| **J** | 使用CMS | 文字列 | HTMLソース内のシグネチャから国内外の主要CMSを多角的に判定（WordPress, baserCMS, EC-CUBE, Movable Type, Drupal, TYPO3, concrete5, Shopify, Wix 等、30種以上を検知対象とする）。非CMSサイトは空欄と出力。 |
| **K** | 用途 | 文字列 | トップページのメタ情報より優先度順に抽出。(1) `<meta name="description">`（`og:description`も可）➔ (2) `<title>` ➔ (3) `<h1>`。**文字数の切り詰めは行わない。** |
| **L** | 問合せ項目 | 文字列 | 問い合わせページと思われるURL・リンクテキストを検出した上で、フォーム内の入力項目ラベルを `aria-labelledby` / `aria-label` / `<label for>` / 祖先要素（`dt`, `th`, `legend`等）から解決して改行区切りで出力。上記で取得できない場合は `th`/`label`/`dt`/`td`/`legend` の総当たり、それでも取得できない場合は `placeholder`/`aria-label`/`title`/`name` 属性値をフォールバックとして使用。HubSpot・Tayori等の外部埋め込みフォームを検出した場合はその旨のテキストを出力。iframe内のフォームも最大2階層まで再帰的に解析する。 |
| **M** | 不可の理由 | 文字列 | **(1) ページ数が0ページ（接続不可・ボット拒否）➔ 「接続不可またはアクセス拒否のため、判定を保留しました。」**<br>(2) ページ数が1〜2ページ ➔ 「クロールできたページ数が極端に少ないため判定を保留しました (取得数: {n}ページ)。」<br>(3) 階層が深すぎて計測不能 ➔ 「サイト階層が深すぎるため、別途サイトエクスプローラー等での確認をお願いします。」<br>(4) 上記以外で `×` 判定となった場合、該当する理由を改行区切りですべて列挙：ページ数超過／3階層以上／ログイン機能あり／添付機能あり／ベーシック認証あり／Captcha使用／ステップ型フォーム／カレンダー機能／サイト内検索機能／チャットボット導入／PDF資料多数／Lightbox等／多言語対応／スクロールアニメーション多用。<br><br>※旧仕様にあった「問い合わせ入力項目が検出できませんでした」という理由は、現状の `RenewalEvaluator` には存在しない。 |

| **O** | 担当 | 文字列 | アプリ実行時にユーザーが手動入力した「担当者名」をそのまま出力。 |

## 2. 非機能要件

### 2.1. 性能・制限事項（スクレイピング制御）

* **スマートSSL＆リダイレクト検証**:
  * セキュリティブロックを緩和するため、ブラウザに擬態した一般的なUser-Agentヘッダーを付与して通信を実行。
  * 初回アクセスは `http://` で行い、`https://` への自動リダイレクトの有無を追跡することで「常時SSL（E列）」を判定。
  * `http://` でリダイレクトされない場合、個別に `https://` 接続を検証する2段構えのフォールバックを搭載。
  * **`http://` 自体への接続が失敗する（ポート80非対応など）HTTPS専用サイトに対しては、`https://` への直接接続を試みるフォールバックを追加**しており、この場合も「SSLあり／常時SSL」と判定できる（旧仕様では判定不能として扱われていた挙動を改善）。
  * `SslChecker` はデフォルトで証明書検証（`verify`）を有効にした状態でリクエストする点に注意。一方でクローラー本体（`WebCrawler`）は巡回漏れ防止のため `verify_ssl=False` をデフォルトとしており、両モジュールでSSL証明書検証の方針が異なる。

* **接続不能時の安全なフォールバック**:
  * DNSエラー、タイムアウト、GoogleやCloudflare等のセキュリティによる403/401エラー（ボット拒否）が発生した場合、プログラムをクラッシュさせず判定不能（`None, None`）として安全に例外をキャッチ。
  * 巡回フェーズへ「ページ数 0」として結果を引き継ぐことで、最終レポートの調査結果（C列）を自動的に『要確認』に分類し、不可の理由（M列）へ適切なエラー理由を出力。

* **クローリングの安全性**:
  * 対象サーバーへの負荷を抑えるため、リクエスト間に約0.04秒のディレイを付与。
  * クローラーは `verify=False` を採用し、SSL期限切れや古いサーバー環境であっても、SSLエラーで処理を中断させることなく確実にHTMLデータを取得。
  * 各HTTPリクエストには `page_timeout`（デフォルト5秒）のタイムアウトを設定。クロール全体には `timeout`（デフォルト30秒）の時間予算を設定し、時間予算を超えた時点でその後の巡回を打ち切る。

* **リンクドメイン正規化 (www.有無の吸収)**:
  * クロール中の内部リンク判定において、`www.` の有無を正規化して吸収し、ドメイン本体の一致のみを厳密に検査する。
  * URLの正規化時、`index.html`/`index.php` の末尾表記やクエリ文字列・フラグメント・末尾スラッシュの差異も統一する。

* **無限リンクトラップの検知**:
  * カレンダーページ等が生成する `/a/a/a` のような単純な繰り返しパスに加え、JS遷移リンクの相対パス誤解決などによって生じる `/blog/2023/01/11/blog/2023/01/11/...` のような**1〜6セグメント単位の塊が連続して2回出現するパターン**も検知し、該当URLへのアクセスをスキップする。

* **添付ファイル・ログイン機能・ベーシック認証検知**:
  * お問い合わせフォーム内に `type="file"` のinputが存在する場合、添付機能ありと判定。
  * URLに `LOGIN_KEYWORDS`（`login`, `signin`, `mypage`, `member`, `account`, `ログイン`, `マイページ`, `会員` 等）が含まれる場合、またはページ内に「ログイン」「サインイン」「マイページ」等のリンク／ボタンテキストを検出した場合、ログイン機能ありと判定。
  * 初回アクセス時、およびクロールループ内で個々のページを取得する際に `response.status_code == 401` を検知した場合、ベーシック認証ありと判定する。サイト全体がベーシック認証で保護されている場合だけでなく、一部の下層ページのみが保護されているケースも検知対象に含まれる。

* **Contactページの早期離脱**:
  * 複雑なサイト構造において問い合わせページが発見できない場合、無限ループや過度なネスト探索を回避するため、iframeの再帰解析は最大2階層までに制限。

* **JSフレームワーク検知**:
  * フォームが検出できなかった場合、Nuxt/Vue/React/Next/Angular/Svelte/Alpine.js/Vite/Remix/Astro等のマーカーがHTML内に存在するかを確認し、SPA/CSRによる取得漏れの可能性をログに記録する（結果には影響しないが、原因切り分けの補助情報とする）。

* **JSレンダリング対応（オプション）**:
  * `render_js=True` を指定した場合、初回ページに限りPlaywrightでレンダリング後のHTMLを取得する。Playwright未導入環境では自動的に通常のHTTP取得へフォールバックする（デフォルトは `False`）。

### 2.2. 処理方式

* **非同期キュー処理**: 複数ドメインが記載されたExcelファイルがアップロードされた場合、Webアプリケーションのメインプロセスとは別のバックグラウンドスレッドで、ドメインを1件ずつ逐次スクレイピングする。
* **進捗の可視化**: 処理中は画面側へ現在の処理件数（例: `25 / 100件 完了`）と進捗率（%）を、約1.5秒間隔の自動リロード（ポーリング）によって通知する。
* **障害時の扱い**: 1ドメインの処理中に例外が発生しても、そのドメインの結果は初期値（0ページ・空欄等）のまま次のドメインの処理へ進む設計になっている。ただし、ジョブ全体を通す `try` ブロックの外側で予期しない例外が発生した場合は、ジョブ全体のステータスが `failed` となり、以降のドメインの処理は行われない。

### 2.3. ロギング

* **ファイル出力**: `utils/logger.py`の`setup_logger()`をアプリ起動時（`main.py`、`st.session_state`による1回限りのガード付き）に呼び出し、コンソールとログファイル（`logs/app_YYYYMMDD.log`）の両方にログを出力する。デフォルトログレベルは`INFO`。
* **処理時間の計測**: `utils/decorators.py`の`measure_time`デコレータを`WebCrawler.crawl_and_analyze`・`SslChecker.check_ssl_status`に適用し、各ドメインのクロール・SSLチェックにかかった時間をDEBUGログとして記録する。
* **処理の開始・完了ログ**: `log_action`デコレータを`ExcelService.export_excel`に適用し、Excel出力処理の開始・完了をINFOログとして記録する。
